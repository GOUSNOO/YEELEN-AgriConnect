# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

YEELEN AgriConnect — full-stack agricultural management app (French UI/comments/domain vocabulary). React frontend (`src/`) + Express/PostgreSQL backend (`server/`), built and deployed as separate services (see Docker section).

Modules: tableau de bord, calendrier, récoltes, cultures & irrigation (capteurs simulés), poulailler (stocks/ventes/livraisons/suivi), clients, fournisseurs, finances, banques, devis/factures (with e-signature), salariés (RH), MFA, planning (generic placeholder logic, see below), observations (field notes).

## Project roadmap (cahier des charges)
Source document: `Feuille_de_route_YEELEN_AgriConnect.pdf` (not in the repo — shared out-of-band, v1.0). Methodology: Agile (Epics/User Stories/MoSCoW/sprints) for product scope, ITIL (service strategy/design/transition/operation/continual improvement) for how the running service is governed. Long-term vision (10-20 years): a full agricultural ERP (crops, livestock, fish farming, stock, equipment, HR, accounting, sales, logistics, transformation, BI, precision agriculture) — deliberately **not** planned in detail now; only the MVP is actively scoped. Business goal at 6 months: ship a free, limited MVP to real farmers with a feedback forum, and let real usage drive the backlog rather than guessing.

**MVP scope (MoSCoW), 6-month horizon:**

**4 milestones (Jalons) after the already-done Jalon 0 (socle)**: Jalon 1 *Consolidation/sécurisation* (backups, hosting, HTTPS, MFA, audit log, full manual E2E testing) → Jalon 2 *Elargissement fonctionnel* (stocks, matériel, RH, facturation) → Jalon 3 *Préparation mise en production* (docs, forum, bug-hardening, user testing) → Jalon 4 *Mise en production* (deploy, open to first farmers, collect feedback).

### Calendrier & Récoltes — now backed by the database (fixed 2026-08-13)

Fixed by extending the schema and following the exact remote-with-local-fallback pattern `AchatModule` already established (`App.jsx:1086-1214`: try the API, fall back to `storageGet`/`storageSet` only if the network call itself fails — keeps the app usable offline without it being the primary store):
- **`calendar_events`** — new table (`server/src/db/migrate.js`), `entreprise_id`/`user_id`/`date`/`type`/`title`/`description`. New `server/src/routes/calendar.js` (`GET`/`POST` only — the UI has no edit/delete, so neither does the route).
- **`recoltes`** — turned out to already exist as an **orphaned table** (confirmed via `\d recoltes` in the live DB and `grep`ping every route file: zero queries against it anywhere), alongside an equally-orphaned `cultures` catalog table (`recoltes.culture_id` FKs to it) — both leftovers from an earlier architecture, abandoned once the app settled on `parcelles.culture` as free text. Reused rather than shadowed with a same-purpose table under a different name: extended it with `user_id`/`parcelle`/`culture`/`qualite`/`destination` columns to match what the `HarvestsModule` form actually captures; `culture_id`/`unite`/`observations` (pre-existing columns) stay unused. New `server/src/routes/recoltes.js`, same `GET`/`POST`-only shape.
- `AgriculturalCalendarModule` and `HarvestsModule` in `App.jsx` rewired accordingly (`getCalendarEvents`/`createCalendarEvent`, `getRecoltes`/`createRecolte` in `src/lib/api.js`, writes go through `safeRequest` for the existing offline-queue mechanism). Verified via the browser: created one of each as the test entreprise, confirmed both rows landed correctly `entreprise_id`-scoped via direct `psql` queries, then cleaned up along with the rest of the test data.

### Traçabilité parcelle → récolte → vente (added 2026-08-13)

Gap-analysis against mature agricultural ERPs (Odoo Farm, Agrivi, Cropio...) found Récoltes/Devis/Finances were disconnected islands — no way to tell which parcelle's harvest a given sale came from. Full context and the two options considered are in memory `project_tracabilite_parcelle_vente`; the user picked the lightweight option (nullable FK tags, no stock/quantity enforcement) over building real lot-depletion tracking, deliberately deferring the latter until the Devis state machine has a stable production track record.

**Investigation finding that simplified the work**: the app has two superficially-parallel "vente" code paths — `cultures_mouvements`/`MovementTab` and `devis_lignes`/`DevisModule` — but only the second is actually live. `MovementTab` (`App.jsx:174-549`) and `createCulturesMouvement`/`updateCulturesMouvement`/`deleteCulturesMouvement` (`src/lib/api.js`) are dead code: imported/defined but never rendered or called anywhere. Both Cultures' and Poulailler's "Ventes" tabs render `<VentesWithDevis>` → `DevisModule`, so `devis_lignes` was the only real anchor point needed.

- `recoltes.parcelle_id` (nullable FK → `parcelles.id`) and `devis_lignes.recolte_id` (nullable FK → `recoltes.id`) added in `server/src/db/migrate.js`. The pre-existing free-text `recoltes.parcelle` column is kept alongside `parcelle_id` for display/fallback, not replaced.
- **Tenant-isolation validation added on both new FKs** — `server/src/routes/recoltes.js`'s `POST /` and `server/src/routes/devis.js`'s `POST /`/`PUT /:id` (via a shared `validerRecolteIds` helper in `devis.js`) verify the referenced `parcelle`/`recolte` actually belongs to `req.user.entrepriseId` before storing the id, silently storing `null` otherwise rather than erroring — mirrors the seriousness the codebase already gives this class of bug (see the `achats_lignes` cross-tenant deletion hole documented above). Verified with real cross-tenant curl calls (two throwaway entreprises, one token per company): a devis ligne referencing another company's `recolteId`, and a récolte referencing another company's `parcelleId`, both came back `null` in the response and in the DB — no leak, no 500.
- Frontend: `HarvestsModule`'s "Parcelle" field is now a `<Select>` sourced from `getParcelles()` (with an "Autre parcelle" free-text fallback) instead of a free-text `Field`, and `DevisModule`'s per-ligne form gained an optional "Récolte liée" `<Select>` sourced from `getRecoltes()`. Both mirror `AchatModule`'s existing fournisseur-dropdown pattern (`App.jsx:1116-1125` load, `~1307-1316` JSX, `~1136-1138` derived display name) verbatim rather than inventing a new one. The devis detail modal resolves `ligne.recolteId` against the already-loaded `recoltes` list and shows a small "🌾 Parcelle A — 13/08/2026" line under the product name when set — traceability that's actually visible, not just stored.
- Accepted limitation: `DevisModule` has no `moduleType` prop (unlike `AchatModule`), so the "Récolte liée" dropdown shows up even when creating a devis from the Poulailler screen, where it's simply not relevant/usable. Not fixed — would need threading a prop through `VentesWithDevis` for no real benefit yet.

### Navigation — sticky header, and a `category` field prepping future grouping (added 2026-08-13)

User feedback (real product/design opinion, not a bug report): the top nav is 15 flat chips (`availableTabs`) that already wrap to 2-3 rows and, worse, weren't pinned — scrolling into any module's content lost access to switching tabs entirely, forcing a scroll back to the top every time. Compared unfavorably to mature ERPs (Odoo, SAP Business One, NetSuite), which group nav into a sidebar/mega-menu and always keep it reachable.

Two changes, deliberately scoped to **not** change the visible layout beyond making it pinned (a real IA redesign — sidebar, grouped mega-menu — was explicitly deferred until there's real usage data to base groupings on):
- **`category` field added to every `availableTabs` entry** (`App.jsx`, `~line 4269`) — `'operations'` (Calendrier/Récoltes/Cultures/Poulailler/Notifications/Observations), `'analyse'` (Assistant IA/Prévisions/Rapports), `'commercial'` (Clients/Fournisseurs), `'finance'` (Finances), `'rh'` (Employés), or `null` for Accueil/Profil. **Nothing reads this field yet** — pure data-prep so a future grouped-nav UI (sidebar or otherwise) is a rendering change on top of already-categorized data, not a data-modeling change bundled with a risky visual redesign.
- **Header made `position: sticky`**: the topbar + online/sync-status row + the nav-chip row were restructured into one shared sticky wrapper (previously the nav-chip row lived inside `dashboard-shell`, a separate, non-sticky sibling — moved to render inside the same wrapper as the topbar, conditioned on `screen === 'dashboard'`, so all three stay pinned together without needing to hand-calculate stacked `top` offsets for multiple independent sticky elements).
  - **Real bug hit and fixed along the way**: `.topbar`'s `backdrop-filter: blur(10px)` (paired with `background: rgba(255,255,255,0.96)`) caused a genuine Chromium rendering glitch once the element became `position: sticky` — inconsistent/stale paints during scroll (topbar appearing to detach, render at the wrong vertical position, or leave blank gaps), reproduced via automated scrolling and confirmed via `getBoundingClientRect()` mismatches against what was actually painted. This is a known bug class (`backdrop-filter` + `position: sticky` compositing in Chromium). Fixed by dropping `backdrop-filter` and making the background fully opaque (`#FFFFFF`) — the blur was pointless anyway once the whole sticky header got its own solid `COLORS.bg` background from the wrapper.
  - Verified via real scrolling (both the module-selection screen and actual dashboard/module content) after the fix: header stays correctly pinned, no repaint artifacts, tab-switching works mid-scroll, `npm test` still green.

### `Card` silently dropped `onClick` — broke selecting anything but the first Client/Fournisseur (fixed 2026-08-13)

User-reported: in Clients, clicking any card other than the first did nothing — the detail panel on the right never updated. Root cause in `src/components/ui.jsx`: `export function Card({ children, style })` only destructured `children`/`style` and forwarded neither `onClick` nor any other prop to the underlying `<div>` — so `<Card onClick={() => setSelectedId(client.id)}>` (`ClientsModule`, `App.jsx`) silently did nothing on every card. The *first* client only ever appeared selected because `ClientsModule`'s load effect auto-selects `loaded[0].id` on mount — not because clicking worked.

Same copy-pasted pattern, same bug, in `FournisseursModule` (`App.jsx`) — confirmed and fixed identically. Grepped for any other `<Card ... onClick` usage in `App.jsx`; these two were the only ones (everything else that needs click behavior already uses `<button>`/`<Button>`, which do handle `onClick` correctly).

### "Configurer votre entreprise" — reappears every login until admin/directeur actually validates it (fixed 2026-08-13, corrected same day)

User-reported: after finishing (or skipping) the post-registration "Configurer votre entreprise" onboarding screen (banques/salariés wizard, `screen === 'onboarding-choice'` in `App.jsx`), it kept coming back on every subsequent login and every page reload — forever, not just for new entreprises.

**First attempt was wrong, corrected the same day after clarifying the actual requirement with the user.** The initial fix persisted a one-time "done" flag in `localStorage` (`agri-onboarding-done`) — any exit from the wizard (skip or complete) marked it permanently done and it never showed again. That's not what was actually wanted: the real spec is (a) only **admin**/**directeur** should ever see this screen, never other roles, and (b) it should keep reappearing **every login** until the entreprise's banking and staffing setup is genuinely resolved — either real data exists, or the director explicitly confirms it isn't needed. A one-time browser flag can't express "resolved" as an ongoing fact about the entreprise, and `localStorage` is scoped to one browser anyway — the same director logging in from a second device would wrongly see it again. Landed on a fully server-driven design instead, per explicit user instruction ("tout doit passer par le serveur").

- **`entreprises.banque_non_requise` / `entreprises.salarie_non_requis`** (both `BOOLEAN NOT NULL DEFAULT FALSE`, `server/src/db/migrate.js`) — explicit "I don't need this" confirmations, one per wizard step.

- **`App.jsx`**: new shared `checkOnboardingNeeded(uiRole)` helper (called from both `handleAuth` and the mount-time token-check effect, replacing the old `storageGet`/`storageSet` calls) — for any role other than `admin`/`directeur` it sets `isOnboarding(false)` **without calling the API at all** (verified via the browser's network tab: zero requests to `/entreprise/onboarding-status` when logged in as `ouvrier`); for admin/directeur it fetches the real status and sets `isOnboarding(!(banqueOk && salarieOk))`. `goToDashboard` no longer marks anything as done — completion is recomputed fresh from the server on every login, not memorized at exit, which is exactly what makes "Plus tard" naturally mean "ask me again next time" instead of "never ask again."
- The wizard's two "Passer cette étape" buttons (`onboarding-banques`, `onboarding-salaries`) were relabeled into real, persisted confirmations instead of silent skips: **"Je n'ai pas de compte bancaire (caisse uniquement)"** calls `updateOnboardingStatus({ banqueNonRequise: true })`, **"Je travaille seul, pas de salarié à ajouter"** calls `updateOnboardingStatus({ salarieNonRequis: true })` — both before advancing to the next screen. The "Suivant"/"Terminer" buttons are untouched: if the director adds a real bank account or employee through `BanquesModule`/`EmployeesModule` on those same screens, `banqueOk`/`salarieOk` are already `true` next login purely from the real data, no confirmation click needed.

## Architecture

### Multi-tenant model
Data is partitioned by **company (`entreprise`)**, not by individual user. Key tables: `users`, `entreprises`, and the join table `entreprise_utilisateurs` (`user_id`, `entreprise_id`, `role`, `statut`) — a user's role is scoped per-company, not global. `server/src/routes/auth.js` shows the full lifecycle: `register` creates a `users` row + an `entreprises` row + the linking `entreprise_utilisateurs` row in one transaction; `login` looks up the active `entreprise_utilisateurs` row to determine role/company.

- JWT payload: `{ sub, email, entrepriseId, role }`, signed/verified with `env.JWT_SECRET`.
- `authRequired` (`server/src/middleware/auth.js`) verifies the JWT and sets `req.user`.
- `requireRole(...roles)` (`server/src/middleware/requireRole.js`) gates routes by `req.user.role` (e.g. `requireRole('admin')` on destructive/admin-only actions in `devis.js`, `entreprise.js`, `salaries.js`).
- Frontend roles (`src/components/roles.js`, `ROLE_DEFINITIONS`): `admin`, `directeur`, `gestionnaire`, `comptable`, `assistant_direction`, `ouvrier` — each maps to a fixed list of allowed UI sections (permissions array), independent of backend `requireRole` checks. `directeur` (added 2026-08-13) mirrors `admin`'s full permission set; `assistant_direction` (added same day) mirrors `comptable`'s scope plus `fournisseurs`. `role` is a free-text column with no DB-level enum/CHECK constraint, so these are a convention enforced only by the frontend dropdown (`App.jsx`'s `EmployeesModule`, the account-creation role `<Select>`) and `requireRole(...)` allowlists on the backend — not a real constraint. README's access matrix predates this and still only lists the original 4 roles; update it if it becomes a source of confusion. This 6-role set is the fixed-roles half of a two-part plan; the other half — letting each entreprise define its own custom roles/permissions — was explicitly scoped out as a separate, much larger effort (a real per-entreprise permissions engine) and is not started.
- **Every route handler scopes its queries by `req.user.entrepriseId`** — this is the actual tenant-isolation boundary; there is no other enforcement layer (no RLS, no ORM-level scoping). When adding a table/route, mirror the existing pattern in `business.js`/`cultures.js`/`poulailler.js` (`WHERE entreprise_id = $1`, insert with both `entreprise_id` and `user_id`).

### Backend structure (`server/src/`)
- `server.js` — Express bootstrap; mounts routes flatly under `/api/*`: `auth`, `business`, `cultures`, `poulailler`, `entreprise`, `salaries`, `banques`, `mfa`, `devis`, `achats`, `observations`, `planning`, `calendar`, `recoltes`. Each route file inlines its own `pg` queries directly — no ORM, no repository layer, no shared query builder.
- `db.js` — the single `pg` `Pool` instance every route imports; it reads DB config straight from `process.env` via its own `dotenv.config()` call. `config/env.js` separately loads the *repo-root* `.env` for `JWT_SECRET`/`PORT`. There's no single shared env-loading entrypoint — check which of the two a given file needs.
- `services/` — cross-route business logic: `mailer.js` (nodemailer/Gmail transport: MFA codes, welcome emails, devis emails), `banquesService.js` (bank account CRUD used by `routes/banques.js`), `planningService.js` (`generatePlan`, used by `routes/planning.js`), `cultureService.js` (`getCulturePlanDetails`: looks up a `parcelles` row by id + `entreprise_id` and returns a **generic, non-agronomic** placeholder intervention schedule — not real crop-specific data, see `POST /api/planning` below).
- `POST /api/planning` (`routes/planning.js`) takes `{ cultureId }` in the body — despite the name, `cultureId` is actually a **`parcelles.id`** (there's no separate "culture" table); it returns a computed intervention plan but does not yet persist it (the DB-save step is commented out as a TODO in the route).
- `utils/` — `financeSync.js` (`syncFinanceEntry`/`updateFinanceEntry`/`removeFinanceEntry`/`syncDevisPaiement`: every vente/achat/facture payment writes a mirrored row into `finances`, categorized `Banque` or `Caisse` depending on whether the company has a `banque_principale` set — this is how cross-module financial consistency is maintained, there are no DB triggers), `mouvementHistorique.js` (audit log of edits/deletes on mouvements, written explicitly by routes, read back via `getPoulaillerHistorique`/`getCulturesHistorique`), `devisPdf.js` (pdfkit invoice/quote rendering, streamed to the response).
- `controllers/observationsController.js` exists but is **dead code** — nothing imports it. The live `/api/observations` logic is inline in `routes/observations.js`, scoped by `entreprise_id` from the JWT like every other route (inconsistent with the file's own comment claiming it needs `companyId` support added).
- Devis (quotes/invoices) is the most elaborate flow: `Brouillon → Envoyé → Signé → Facturé/Non payé/Payé partiellement`, with a public token-based route (`/devis/public/:token`, no auth) for client-side viewing + e-signature, PDF generation both for the owner and via public token, and per-échéance (installment) payment tracking that syncs into `finances` only when an installment is actually paid.

### Database migrations
`server/src/db/migrate.js` is now the **single** source of schema truth — one large, hand-maintained, idempotent script (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, `CREATE TABLE IF NOT EXISTS`), not versioned beyond this one file. `migrations/001_create_observations_table.sql` at the repo root used to be a second, unconnected mechanism (plain SQL, no runner, had to be applied by hand) — its `CREATE TABLE observations` was folded into `migrate.js` 2026-08-13, so that file is now superseded/historical only; don't apply it separately, everything runs through `migrate.js`.

Running migrations from the host (rather than `docker exec agri-app-backend-1 node src/db/migrate.js`) requires pointing at the Docker `db` container's host port explicitly (`5433`, see below) — `server/.env`'s `DB_PORT` must stay `5432`, since that's what the **backend container** needs internally to reach `db:5432` over the Compose network (host-side port remapping never affects container-to-container traffic). `docker exec` remains the simplest correct way to run migrations and is what's documented in Commands above.

### Local dev environment on this machine — Docker Desktop, port layout, and a resolved port collision
The app normally runs as 4 Docker Compose services (`docker-compose up --build`):

| Service | Image/build | Host port | Notes |
|---|---|---|---|
| `db` | `postgres:18-alpine` | **`5433:5432`** | app data lives here (host port intentionally *not* 5432 — see below) |
| `backend` | `./server` (Dockerfile) | `4000:4000` | `DB_HOST` overridden to `db` (Compose network) in `docker-compose.yml`; `DB_PORT` stays `5432` (container-internal, from `server/.env`) — these are independent of the host-side `5433` mapping |
| `frontend` | root `Dockerfile` (Vite build → nginx) | `8090:80` | `VITE_API_URL` baked in at build time |
| `backup` | `server/Dockerfile.backup` | *(none published)* | `pg_dump` every 6h, see Backups above |

**There is also a native Windows PostgreSQL service (`postgres.exe`) permanently listening on port 5432 on this machine, independent of Docker** — confirmed by querying it directly (a different, smaller dataset than the app's real data). `db`'s host port was deliberately moved to **`5433`** (2026-08-12) to stop colliding with it. Consequences:
- **pgAdmin** (or any host-side tool/script) must connect to `localhost:5433` for the real app database — `localhost:5432` is now unambiguously the native Windows Postgres, not Docker's.
- Container-to-container traffic (backend → db) is unaffected either way — it always uses the container-internal port 5432 regardless of the host mapping, which is why no other file needed to change for this fix.

### Backups
`server/Dockerfile.backup` + `server/backup.sh`: a sidecar container loops forever, running `pg_dump` every 6 hours into `/backups`, keeping only the 14 most recent dumps. `backups/` (gitignored) and the committed `agri_app_backup.dump` at the repo root are artifacts of this/manual dumps, not something the app reads at runtime.

**Verified restorable (2026-08-12)**: restored the latest dump into a throwaway database (`pg_restore` inside the `db` container) and confirmed row/table counts matched the live DB exactly. The restore mechanics work.

**Found and fixed (2026-08-12): silent empty-dump failures.** 3 of the last 14 rotated dumps were 0 bytes — `backup.sh` didn't check `pg_dump`'s exit code robustly (`set -e` alone wasn't catching it in practice) or verify the output file was non-empty, so failed backups were silently kept and rotated in as if valid. Likely cause: `backup`'s `depends_on: - db` (old short form) only waited for the `db` *container* to start, not for Postgres inside it to actually be ready — a classic cold-start race. Fixed:
- `docker-compose.yml`: `db` now has a `healthcheck` (`pg_isready`); `backend` and `backup` now `depends_on: db: condition: service_healthy` instead of the old unconditional form.
- `server/backup.sh`: now explicitly checks `pg_dump`'s exit code and that the resulting file is non-empty (`[ -s "$BACKUP_FILE" ]`) before declaring success; deletes and fails loudly (`exit 1`) otherwise instead of leaving a useless 0-byte file in the rotation.
- The 3 pre-existing empty dumps were deleted from `backups/`.

Not yet done: no alerting on backup failure (a failed cycle just logs and waits for the next 6h attempt), and no automated restore-test — the verification above was a manual one-off.

### Testing (two independent Jest setups — frontend and backend)
This is a two-project repo (`src/` and `server/` each have their own `package.json`/`node_modules`), and each now has its own Jest config; they must not be merged.
- Frontend (root): `babel.config.cjs` + `"jest": { "testEnvironment": "jsdom", "testPathIgnorePatterns": ["/node_modules/", "/server/"] }` in the root `package.json`. Without the `testPathIgnorePatterns` entry, root `npm test` would also walk into `server/` and try to run backend tests under the frontend's jsdom + `node_modules` — that crashes (backend deps like `pdfkit`/`fontkit` aren't set up for a browser-like jsdom environment). `@babel/preset-env`/`@babel/preset-react` and `jest-environment-jsdom`/`@testing-library/dom` are devDependencies for this.
- Backend (`server/`): its own `server/babel.config.cjs` (`@babel/preset-env` only, no React) + `jest`/`@babel/preset-env` devDependencies + `"test": "jest"` script. Test lives at `server/src/test/devisPdf.test.js`, next to `server/src/utils/devisPdf.js`.
